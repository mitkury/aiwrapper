# Self-hosted voice on one rented GPU

Proposed pilot, November 21, 2026. Choose a Runpod Community Cloud on-demand Pod with one 24 GB RTX 3090 in a region near the tester. The first milestone is one English-speaking user talking to the simulator, interrupting a reply and asking about the room. All model inference runs on the Pod. The existing browser playground and Rust session host run on the developer's computer.

## Hosting decision

| Service | Startup and shutdown | What we pay for |
| --- | --- | --- |
| **Runpod Pod** | Start and stop from the console or CLI. Allow several minutes for a fresh image plus the initial model downloads. A cached restart still loads the models into memory. Stopping releases the GPU, so resuming on the same machine depends on availability. | The 3090 lists at $0.22/hour on Community Cloud. Compute is metered by the second while running, including idle time. Runpod requires credit for one hour to deploy. Local persistent disk costs $0.10/GB/month running and $0.20/GB/month stopped, prorated by the second. Pod traffic is included. [GPU rates](https://www.runpod.io/gpu-models/rtx-3090) · [Billing](https://docs.runpod.io/pods/pricing) · [First deployment](https://github.com/runpod/docs/blob/main/tutorials/pods/run-your-first.mdx) · [Restart availability](https://docs.runpod.io/pods/troubleshooting/zero-gpus) |
| **Vast.ai on-demand** | Pick a host with the image cached. Vast says a fresh image pull can take 10–60 minutes. Stop the instance to release compute, or destroy it to release its local storage too. | Per-second compute, retained storage and host-specific transfer charges in both directions. The published 3090 market snapshot showed a $0.20/hour median. A cheaper nearby host is worth considering if Runpod has no local inventory. [Quickstart](https://docs.vast.ai/guides/get-started/quickstart) · [Billing](https://docs.vast.ai/guides/instances/pricing) · [Market prices](https://vast.ai/article/how-much-does-it-cost-to-rent-a-gpu-in-the-cloud-live-pricing-guide) |
| **Modal** | An incoming request can start the container. Modal quotes about a second for container boot. GPU scheduling and model loading add time before the first reply. After the session ends, the worker can scale to zero. | L4 GPU at about $0.80/hour, plus CPU and RAM, metered by the second. Keeping the GPU warm during the idle window also costs money. [Pricing](https://modal.com/pricing) · [Cold starts and idle billing](https://modal.com/docs/guide/cold-start) |

Runpod lets us run a stock Linux GPU environment, forward ports over SSH and choose exactly when to shut it down. That makes it the simplest place to diagnose a silent microphone or a slow model. For a **30-minute powered-on test**, the listed 3090 costs **$0.11 in compute**. Keeping a stopped 50 GB volume for a full month costs **$10**. Container disk is temporary. Keep weights on the persistent volume and keep the reproducible setup in Git. [Pod pricing and storage](https://docs.runpod.io/pods/pricing)

## What to build

1. **Provision a repeatable model server.** Start from a pinned Runpod PyTorch/CUDA image with direct TCP SSH support. Target 8 vCPUs, 32 GB host RAM and 50 GB persistent disk. Use one bootstrap script to install pinned dependencies, check free disk, cache model revisions under `/workspace` and launch two loopback services, one for language and one for speech. Forward their ports through SSH. Keep the playground on localhost for microphone access. Tie readiness to a short successful transcription, generation and synthesis. Surface the failing stage and error if a probe fails. [Runpod SSH requirements](https://docs.runpod.io/pods/configuration/use-ssh)
2. **Connect streaming speech input.** Add a self-hosted option at the Rust example's existing [transcription boundary](../../../native/src/speech-stream.rs). Stream mono PCM to the speech service over WebSocket. Resample incoming 24 kHz audio continuously to 16 kHz there. Use CPU Silero VAD to signal confirmed speech onset and sherpa-onnx's English streaming Zipformer for partial text and endpointing. Use one increasing numeric ID per utterance, emit one final transcript, and flush the recognizer on manual end-of-turn. The [cascade runtime](../../../native/src/live/cascade.rs) already interrupts playback on speech start and commits the user turn on final text. Tune speech onset and trailing silence independently with headset and speaker tests. [Silero VAD](https://github.com/snakers4/silero-vad) · [Streaming Zipformer](https://k2-fsa.github.io/sherpa/onnx/python/streaming-websocket-server.html)
3. **Connect language and voice output.** Serve Qwen3-VL-4B-Instruct through vLLM's OpenAI-compatible chat endpoint on the GPU. Use the existing compatible provider with a bounded context, one concurrent request and latest-frame camera input for the pilot. Verify streaming text, one room image and a tool call with the selected model template. Serve Kokoro-82M on CPU through the speech service. Implement the Rust `SpeechOutput` adapter to return mono PCM with its actual sample rate for each text segment. Propagate cancellation and discard late audio. Keep one model copy warm across turns. [Qwen model card](https://huggingface.co/Qwen/Qwen3-VL-4B-Instruct) · [Kokoro model card](https://huggingface.co/hexgrad/Kokoro-82M)
4. **Expose one simulator preset.** The [Rust example](../../../native/examples/cascade.rs) currently constructs Deepgram directly, and the [playground bridge](../../../playground/src/lib/server/native-cascade.ts) checks for cloud speech keys. Add an explicit self-hosted preset to both. Resolve endpoint addresses from server-side configuration. Show connecting, listening, interim transcript and playback status. Report a missing tunnel, unavailable service or dead audio stream in the existing session event view. Use the existing playback acknowledgement and history correction paths when the user talks over a reply.

## Access and operating procedure

For deployment, supply a funded Runpod account and a restricted Runpod API key locally as `RUNPOD_API_KEY`, with access to list inventory and create, inspect, start, stop and delete the pilot Pod. Register a dedicated SSH public key on the account and make its matching identity available through the local SSH agent. The model artifacts are public. Credentials belong in the local secret environment, outside chat, Git, the browser and the Pod image. [Runpod credentials](https://docs.runpod.io/get-started/credentials) · [SSH setup](https://docs.runpod.io/pods/configuration/use-ssh)

Proposed first-run limit is **one GPU for one hour at up to $0.22/hour compute**, plus prorated disk. The deployment helper should check the live offer for price, region and direct SSH before creating anything, record the Pod ID, set a provider-side one-hour stop timer on creation and reuse the recorded Pod on retry. If no offer meets the limit, report availability and price. For a later session, restart the Pod, re-arm and verify its stop timer, refresh the SSH address, restore the tunnels and run the readiness probes. If the original GPU is occupied, report that before offering a fresh deployment. [Pod lifecycle and timers](https://docs.runpod.io/runpodctl/reference/runpodctl-remove-pods)

At the end of a test, close the session, stop the Pod and verify its stopped state through the API. Retain the volume only if another session is planned. After the final test, save the timing report locally, delete the pilot Pod and its local volume, and verify removal in the account. The implementation should report running time, the quoted rate and remaining storage charges at shutdown.

## Acceptance

- Run `npm run native:check`, `npm run native:test:cascade` and `npm run check:playground`. Add deterministic fixtures for partial/final ordering, speech onset during playback, cancellation, disconnect and retry.
- From the simulator, speak a known phrase, observe the matching final transcript, hear a relevant reply, ask about a visible object, and exercise one tool. Interrupt a long spoken reply, verify old audio stops and inspect the next request's corrected history. Repeat after disconnect and reconnect. Unplug the microphone and stop each model service in turn to verify a visible, stage-specific error.
- Time a fresh deploy and a stopped-Pod restart separately from request to first successful audio probe. For ten warm conversational turns, record median and worst end-of-speech to first audible reply, and for ten interruptions record speech onset to playback silence at the client. Initial targets are a median under 1.5 seconds for a reply and 300 ms for a cut. These are pilot targets pending measurement. Report endpointing, model, synthesis and playback delays separately.
- Stop the Pod, confirm GPU billing has ended and report the retained disk size and rate. The pilot is complete once another developer can reproduce the run from the checked-in setup and the measured latency and cost are recorded.
