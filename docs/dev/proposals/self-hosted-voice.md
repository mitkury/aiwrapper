# Self-hosted voice on one rented GPU

Proposed pilot, November 21, 2026. Choose a Runpod Community Cloud on-demand Pod with one 24 GB RTX 3090 in a region near the tester. The first milestone is one English-speaking user talking to the simulator, interrupting a reply and asking about the room. All model inference runs on the Pod. The existing browser playground and Rust session host run on the developer's computer.

## What streams today

In Cascade, the browser sends microphone blocks throughout the utterance. Deepgram returns speech onset and interim transcripts as they arrive. Rust interrupts an active reply at speech onset, displays revisions, and starts the LLM once on the committed, nonempty transcript. The LLM streams text, Rust hands speakable phrases to TTS during generation, and PCM plays as it arrives. The latency calculation below starts at the last voiced sample, so it already credits the transcription done while the user is speaking. Speculative replies to unstable partials would require handling revised words, abandoned audio and premature tool calls. Keep that as a separate experiment if endpointing dominates. The simulator's **Gemini Live** route already sends audio and room images directly over its provider session and deserves a separate baseline. [Rust cascade](../../../native/src/live/cascade.rs) · [Flux events](../../../native/src/speech-stream.rs) · [Live transport](../../../native/src/live/socket.rs)

During a connected room session the browser samples the rendered view at one 640 × 360 JPEG per second, including during assistant speech. In Cascade the Rust host buffers those frames. On turn commit it freezes a timestamped batch. The playground's default Recent policy selects up to 12 images within its byte and age limits. Tool continuations reuse the frozen batch. On subsequent turns older camera pixels are pruned while conversation text and tool results remain. Test both “what is in front of me?” and “what did I just walk past?” using this existing behavior. Latest-only is a useful timing comparison. [Visual context policy](../../native-vision.md)

## Context on the 3090

Qwen3-VL-4B-Instruct has **262,144 native positions** shared by the formatted prompt, visual inputs and generated response. The advertised million-token extension requires a different serving configuration. For a single sequence with a BF16 attention cache, the published configuration gives 36 layers × 8 key/value heads × 128 dimensions × 2 arrays × 2 bytes = **144 KiB per token**. That is **36 GiB for the cache alone** at the full native window. At **16,384 tokens** the same calculation is **2.25 GiB**, leaving space on a 24 GB card for weights, the vision encoder, activations and runtime allocations. Actual vLLM reservations and peak memory must be measured on startup and under load. [Qwen model configuration](https://huggingface.co/Qwen/Qwen3-VL-4B-Instruct/blob/main/config.json) · [vLLM serving guidance](https://docs.vllm.ai/projects/recipes/en/latest/Qwen/Qwen3-VL.html)

Start vLLM at 16,384 tokens and one concurrent sequence. Allow up to 12 **image** inputs and disable video input. With the standard 32-pixel visual grid, a 640 × 360 frame rounds to 640 × 352, about **220 visual tokens**. Twelve such frames use about **2,640**. Reserving the cascade's current 1,024 output tokens leaves roughly **12,720** for instructions, tools, history, current text and message/image formatting. Verify actual prompt usage against the pinned processor. Test one near-limit turn and surface a clear session-reset message when full. Compression can wait until measured sessions need it. [Qwen image processing](https://github.com/QwenLM/Qwen3-VL/blob/main/qwen-vl-utils/src/qwen_vl_utils/vision_process.py) · [Processor settings](https://huggingface.co/Qwen/Qwen3-VL-4B-Instruct/blob/main/preprocessor_config.json)

## What to build

1. **Provision a repeatable model server.** Start from a pinned Runpod PyTorch/CUDA image with direct TCP SSH support. Target 8 vCPUs, 32 GB host RAM and 50 GB persistent disk. Use one bootstrap script to install pinned dependencies, check free disk, cache model revisions under `/workspace` and launch loopback endpoints for language, transcription and synthesis. Forward their ports over one SSH connection. Keep the playground on localhost for microphone access. Tie readiness to a short successful transcription, generation and synthesis. Surface the failing stage and error if a probe fails. [Runpod SSH requirements](https://docs.runpod.io/pods/configuration/use-ssh)
2. **Connect streaming speech input.** Add a self-hosted option at the Rust example's existing [transcription boundary](../../../native/src/speech-stream.rs). Stream mono PCM to the speech service over WebSocket. Include the adapter’s accepted 16 kHz input rate in the cascade connected event. The browser already reads this field and resamples capture to that rate. Verify the sample count and ordering through the bridge with a known-duration fixture. Use CPU Silero VAD to signal confirmed speech onset and sherpa-onnx's English streaming Zipformer for partial text and endpointing. Use one increasing numeric ID per utterance, emit one final transcript, and flush the recognizer on manual end-of-turn. The [cascade runtime](../../../native/src/live/cascade.rs) already interrupts playback on speech start and commits the user turn on final text. Tune speech onset and trailing silence independently with headset and speaker tests. [Silero VAD](https://github.com/snakers4/silero-vad) · [Streaming Zipformer](https://k2-fsa.github.io/sherpa/onnx/python/streaming-websocket-server.html)
3. **Connect language and voice output.** Serve Qwen3-VL-4B-Instruct through vLLM's OpenAI-compatible chat endpoint on the GPU. Use the existing compatible provider with the context and image limits above. Keep recent-frame selection available from the first visual test. Verify streaming text, one room image and a tool call with the selected model template. Point the existing Rust PCM speech client at a pinned CPU Kokoro server supporting OpenAI-compatible `/v1/audio/speech` and mono 24 kHz PCM. Give this preset its own loopback endpoint and local credential handling so a cloud OpenAI key never reaches it. Propagate cancellation and discard late audio. Keep one model copy warm across turns. [Qwen model card](https://huggingface.co/Qwen/Qwen3-VL-4B-Instruct) · [Kokoro model card](https://huggingface.co/hexgrad/Kokoro-82M) · [Kokoro interface](https://github.com/remsky/Kokoro-FastAPI/blob/master/docs/integrations/openai.md) · [Rust speech client](../../../native/src/speech.rs)
4. **Expose one simulator preset.** The [Rust example](../../../native/examples/cascade.rs) currently constructs Deepgram directly, and the [playground bridge](../../../playground/src/lib/server/native-cascade.ts) checks for cloud speech keys. Add an explicit self-hosted preset to both. Resolve endpoint addresses from server-side configuration. Show connecting, listening, interim transcript and playback status. Report a missing tunnel, unavailable service or dead audio stream in the existing session event view. Use the existing playback acknowledgement and history correction paths when the user talks over a reply.

## Access and operating procedure

For deployment, supply a funded Runpod account and a restricted Runpod API key locally as `RUNPOD_API_KEY`, with access to list inventory and create, inspect, start, stop and delete the pilot Pod. The deployment helper can generate a dedicated SSH identity locally and supply only its public half in the official PyTorch container’s `PUBLIC_KEY` setting during Pod creation. An existing authorized SSH identity also works. Only the SSH TCP port needs to be exposed. The model artifacts are public. Credentials belong in the local secret environment, outside chat, Git, the browser and the Pod image. [Runpod credentials](https://docs.runpod.io/get-started/credentials) · [SSH setup](https://docs.runpod.io/pods/configuration/use-ssh) · [Runpod container startup](https://github.com/runpod/containers/blob/main/container-template/start.sh)

Proposed first-run limit is **one GPU for one hour at up to $0.22/hour compute**, plus prorated disk. The deployment helper should check the live offer for price, region and direct SSH before creating anything, record the Pod ID, set a provider-side one-hour stop timer on creation and reuse the recorded Pod on retry. If no offer meets the limit, report availability and price. For a later session, restart the Pod, re-arm and verify its stop timer, refresh the SSH address, restore the tunnels and run the readiness probes. If the original GPU is occupied, report that before offering a fresh deployment. [Pod lifecycle and timers](https://docs.runpod.io/runpodctl/reference/runpodctl-remove-pods)

At the end of a test, close the session, stop the Pod and verify its stopped state through the API. Retain the volume only if another session is planned. After the final test, save the timing report locally, delete the pilot Pod and its local volume, and verify removal in the account. The implementation should report running time, the quoted rate and remaining storage charges at shutdown.

## How fast could a warm turn be?

The comparison starts at the user's last voiced microphone sample and ends when the first reply audio starts playing. Most transcription happens while the user speaks. Below is a **planning calculation** for one nearby 3090, loaded models, a short conversation, no tools and no image. Each row allocates time on the path to the first audible phrase. The first three rows cover server-side work. The transport row includes all trips between the developer's Rust host and the Pod.

| Stage | Illustrative warm turn | Assumption to test |
| --- | ---: | --- |
| Finalize the transcript | 450 ms | Tuned endpoint plus recognizer flush. The sherpa-onnx example uses 1.2 s of trailing silence for one common rule. Using that setting adds at least 750 ms to this example on turns that hit the rule. Shorter thresholds can cut off natural pauses. [Recognizer configuration](https://github.com/k2-fsa/sherpa/blob/master/docs/source/onnx/python/streaming-websocket-server.rst) |
| Process the prompt and produce a speakable phrase | 400 ms | Budget 200 ms to first text, then ten more tokens at an assumed 50 tokens/s. A short sentence boundary can release immediately. Otherwise the Rust segmenter can wait for a 200 ms timer tick once enough complete words accumulate. Image encoding, longer histories and tool calls need their own trials. [Cascade segmentation](../../native-cascade.md) |
| Synthesize first phrase with Kokoro on CPU | 500 ms | A budget for a short phrase on the rented CPU. Chunk length matters. One Kokoro server reports about 3.5 s to first output on an older i7 at its published 200-token chunk setting. [Kokoro server benchmark](https://github.com/remsky/Kokoro-FastAPI) |
| Transport, scheduling and playback | 150 ms | Allow about three 40 ms round trips for STT, language and speech plus 30 ms of scheduling and audio buffering. Measure RTT from the test client. |
| **Last voiced sample to first playback** | **1.50 s** | **2.25 s** with 1.2 s endpointing and the other assumptions fixed. A 1 s synthesis delay would raise those two examples to **2.00 s** and **2.75 s**. |

**Cloud comparison, November 21, 2026.** In one Rust host session, three successive typed turns asking the color of a ripe banana took **2.349, 2.233 and 2.035 s** from send to first PCM at the host. The first synthesis requests went out at **1.070, 0.968 and 0.914 s** respectively. This used the playground's default Anthropic model and OpenAI `gpt-4o-mini-tts`, voice `alloy`, with camera and microphone off. It excludes endpointing, browser playback and hardware output delay. The corresponding model-plus-synthesis estimate above is 0.90 s before transport. Both sides still need the same audio fixtures, camera settings and playback clock before claiming an end-to-end speedup.

The Flash configuration deserves its own baseline. Deepgram reports about **260 ms median** for Flux to detect the end of a turn, and ElevenLabs reports about **100 ms server-side** to first audio for Flash v2.5. Those figures cover individual stages and omit client transport, the language model and playback. At the illustrative local timings, those cloud stages could already lead by roughly 0.6 s combined. [Flux timing](https://developers.deepgram.com/docs/flux/nova-3-migration) · [Flash timing methodology](https://elevenlabs.io/docs/eleven-api/concepts/latency-methodology)

**Interruption** takes a shorter route. For example, three consecutive 32 ms Silero speech frames, a 40 ms network round trip and 40 ms to dispatch and silence playback total **176 ms**. The browser sends 4,096-sample blocks, about 85 ms at 48 kHz. Waiting for the next block can bring the example to roughly 180–260 ms before additional device latency or echo rejection. [Microphone capture](../../../playground/src/lib/comps/NativeVoice.svelte) Test the 300 ms target alongside false interruptions on pauses, background speech and speaker echo. [Silero frame size](https://github.com/snakers4/silero-vad/wiki/Examples-and-Dependencies)

## Acceptance

- Run `npm run native:check`, `npm run native:test:cascade` and `npm run check:playground`. Add deterministic fixtures for partial/final ordering, speech onset during playback, cancellation, disconnect and retry.
- From the simulator, speak a known phrase, observe the matching final transcript, hear a relevant reply, ask about a visible object, and exercise one tool. Interrupt a long spoken reply, verify old audio stops and inspect the next request's corrected history. Repeat after disconnect and reconnect. Unplug the microphone and stop each model service in turn to verify a visible, stage-specific error.
- Time a fresh deploy and a stopped-Pod restart separately from request to first successful audio probe. Replay the same ten warm conversational turns on each stack with the same client, then repeat with one identical room image per turn and with matched recent-frame batches up to 12. Log prompt tokens, time to first model text, first playback and peak GPU memory per mode. Score the room answers against visible objects and prior views. Score transcript accuracy and false turn endings on mid-sentence pauses. For each set, record median and worst end-of-speech to first audible reply, and for ten interruptions record speech onset to playback silence at the client. Initial targets are a median under 1.5 seconds for a reply and 300 ms for a cut. These are pilot targets pending measurement. Report endpointing, model, synthesis and playback delays separately.
- Stop the Pod, confirm GPU billing has ended and report the retained disk size and rate. The pilot is complete once another developer can reproduce the run from the checked-in setup and the report includes the commit, model revisions, actual host and region, latency and grounding results, any failed checks, a replay procedure, cost and final resource state. Use prerecorded microphone input for repeatable browser tests. Label physical microphone, speaker echo and perceived audio quality separately when a listener has tested them. A full cloud comparison needs credentials for the specific reference services.
